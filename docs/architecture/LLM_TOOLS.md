# Что доступно LLM в «Бункере»

[Интерактивная схема](llm-tools.html) показывает интерфейс **игрока**, доступный
в текущем коде. В игре есть один запрашиваемый инструмент и три типа JSON-действий.

## Инструмент: search_documents

Игрок записывает запрос в `Intent.search_query`. После выбора выступающего
оркестратор исполняет `Store.search(game_id, round, query)` и сохраняет событие
с именем `search_documents`. Вызов не объявлен как native function calling в
Responses API: модель запрашивает поиск через поле структурированного ответа.
Служебные `game_id` и `round` задаёт код, а не игрок.

| Свойство | Фактическое поведение |
|---|---|
| Когда можно запросить | При подаче заявки `Intent` в свободной дискуссии |
| Условие исполнения | Заявка выбрана, `search_query` непустой |
| Область поиска | Документы этой партии, доступные в текущем раунде |
| Ограничение | Максимум один поиск на выбранную реплику; исполнение сохраняется при повторе речи |
| Результат | До трёх объектов `{id, title, text}`, каждый `text` до 600 символов |
| Возврат модели | `task.search_results` в новом `PlayerView` перед созданием `Speech` |
| Использование | Игрок может сослаться на идентификаторы документов в `Speech.citations` |

Запрос рекомендуется формулировать в 1–3 ключевых словах. Поиск выполняется
локально через SQLite FTS5; карточки участников и будущие документы не индексируются
в доступную игроку область. Результаты получает выступающий; другие игроки видят
только опубликованную речь и ссылки, которые он включит в неё.

## Игровые действия

Это контракты ответа на запрос сервера. Модель не выбирает произвольный тип действия
в любое время: сервер сообщает текущий этап и допустимую схему.

| Контракт | Поля | Что выбирает игрок |
|---|---|---|
| `Intent` | `kind`, `reply_to`, `goal`, `search_query`, `note` | Пропустить, ответить, возразить или поднять тему; при необходимости запросить поиск |
| `Speech` | `text`, `stage_direction`, `addressed_to`, `reveal`, `citations`, `note` | Что сказать, к кому обратиться, какие допустимые карты раскрыть и какие источники указать |
| `Vote` | `candidate_id`, `reason`, `note` | Против кого проголосовать и как объяснить решение |

`Speech.reveal` доступен только при обязательном раскрытии: ровно две новые
характеристики, в первом раунде одна из них — профессия. Код публикует значения
из сохранённой карточки. В дискуссии, последнем слове и защите `reveal=[]`.

`note` — личное краткое намерение, поле принятого действия. Для следующего вызова
сервер автоматически подставляет его в `self.note`. Отдельных инструментов чтения
или записи памяти нет. `history`, собственная полная карточка и публичные сведения
об остальных тоже приходят в `PlayerView` автоматически.

## Другие роли

С версии промптов `bunker-2.1` лимит обычной речи и ведущего — 1200 символов,
защиты/последнего слова — 700, note — 1000, reason — 600, goal — 400,
stage_direction — 240. Общий бюджет игрового JSON — 2400 output-токенов.
HTML-схема и её квитанция фиксируют предыдущую версию 2.0; интерфейсы действий
и поиск остаются теми же, подписи старых лимитов в этом снимке не обновлялись.

Ведущий возвращает `Narration`: текст и установленные кодом идентификаторы исхода.
Подготовка возвращает `World` и `Character`. Поисковых или иных вызываемых
инструментов этим ролям сейчас не предоставлено.

REST-команды сайта, чтение SQLite, SSE, выбор очереди, жеребьёвка и инспектор
контекстов — возможности сервера/зрителя, не инструменты LLM. Доступ к интернету,
файловой системе, shell и чужим закрытым карточкам игрокам не предоставлен.

## Основания и проверка

- [JSON-контракты](../../bunker/domain.py): `Intent`, `Speech`, `Vote`, `Narration`.
- [Оркестрация](../../bunker/engine.py): этапы `intents` и `speech`, событие `tool_result`.
- [Поиск](../../bunker/storage.py): `Store.search`.
- [Контекст](../../bunker/context.py): `player_view`.
- [Вызовы модели](../../bunker/provider.py): `YandexProvider.complete`.

Подписи схемы русские; встроенное меню и `html lang` просмотрщика используют
английский интерфейс Archify. [Исходная спецификация](llm-tools.json).
