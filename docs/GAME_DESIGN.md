# Правила и архитектура

## Партия

6 игроков, 3 места, 3 раунда. В каждом раунде: событие ведущего → раскрытие двух
характеристик каждым → до 8 реплик свободной дискуссии → последнее слово каждого →
предварительное закрытое голосование → защитная речь каждого лидера →
решающее закрытое голосование → одно изгнание. Первая пара характеристик
обязательно содержит профессию; к третьему голосованию у оставшихся раскрыты все 6.

Каждый игрок стремится остаться, а не максимизировать абстрактную «пользу группы».
Можно блефовать о нераскрытом и давать ложные обещания. Официальные карточки
публикуются только из сохранённых данных; модель не меняет их содержимое.

## Конечный автомат

`preflight → setup → ready / opening → reveal → intents ↔ speech → closing → vote
→ defense → final_vote → eliminate → aftermath → advance / epilogue → done`.

Новые партии используют правила 2.0. В сохранённых партиях 1.0 прежний переход:
`vote → [runoff] → eliminate`. Архивные события не изменяются.

Код раздаёт шесть характеристик каждому из авторского каталога `cards.py`;
сценарист сохраняет их дословно, создавая характер и голос. Для старых партий
сохраняется прежний способ подготовки. LLM создаёт мир и персонажей короткими
отдельными запросами. До начала
игры они объединяются в один валидированный Scenario. Это ограничивает время
одного запроса 60 секундами и позволяет переиспользовать успешно созданные части.
Большой единичный запрос Scenario в первом реальном испытании превышал 60 секунд;
эти неудачные попытки сохранены в журнале.

Заявки собираются параллельно по одному публичному снимку. Приоритет: прямой ответ
адресата → возражение/ответ к последней реплике → новая тема. Далее меньшее число
выступлений и вращающийся порядок мест. Предыдущий автор не допускается;
квота 2 реплики на игрока. После выбора отдельный вызов формулирует саму реплику.
Старые заявки истекают и не превращаются в произнесённые слова.

Дискуссия закрывается после 8 реплик,600 секунд её активного выполнения или общего
отказа допустимых участников просить слово. Перебивания происходят между репликами.
Пауза не расходует время дискуссии.

После принятой публичной реплики сервер выдерживает время на чтение:
`clamp(len(text) / 35, 4, 40)` секунд; после голосования и изгнания — 6 секунд.
Это отдельное ожидание оркестратора, не игровое действие LLM. Следующий запрос
начинается только после него. У оставшегося времени и UTC-дедлайна есть сохранённый
снимок; ручная пауза замораживает отсчёт, продолжение восстанавливает его.
При аварийном перезапуске показывается сохранённое окно чтения без повторения речи.
Команда `next` требует event_seq текущего ожидания: запоздалое нажатие не пропускает
следующий ход. Технические события чтения не входят в публичную историю.

Голоса каждого бюллетеня собираются без публикации соседних текущих решений.
Первый результат лишь определяет защитников, включая всех лидеров при ничьей.
Каждый получает одну речь до 700 символов, без нового официального раскрытия.
После защиты решающий выбор снова открыт против любого другого оставшегося.
Ничью решающего разрешает `SHA256(seed:round:sorted_tied_ids) mod len(tied_ids)`.
Seed сохранён до игры. Никаких дополнительных циклов защиты и голосования нет.

Изгнание означает остаться снаружи на откуп судьбе, а не подтверждённую смерть.
Подробное сравнение с опубликованными правилами и набор категорий:
[RULES_RESEARCH.md](RULES_RESEARCH.md).

## Данные и контекст

Ядро `rules` не вызывает модели. `context` формирует отдельный PlayerView:
инструкции, своя полная карточка, публичные характеристики остальных, публичная
история, своя заметка и задача. Ни полный GameState, ни будущие события не передаются
игроку. Ведущий получает публичную историю и только текущее разрешённое событие.
Зритель видит все сведения через отдельное API; его интерфейс не подаёт данные игрокам.

Инструмент `search_documents` выполняет FTS5-поиск максимум один раз для выбранной
заявки; до 3 фрагментов по 600 символов. Будущие документы фильтруются по раунду.
Запрос и результаты доступны в журнале событий, а результаты — в контексте выступления.

## Надёжность

SQLite хранит состояние, события с возрастающим seq и все попытки вызовов.
Принятый ответ сохраняется до применения игрового действия; постоянный action_key
предотвращает повторный платный вызов при возобновлении сохранённого шага.
Параллельный сбор сохраняет успешные ответы, даже если соседний запрос не удался.
Каждое действие имеет максимум 4 попытки; таймаут одной попытки — 60 секунд,
включая чтение потока. Между попытками задержки 1/2/4 секунды; затем техническая пауза.
При новом явном продолжении разрешается новая ограниченная серия попыток.
Сохраняются исходная ошибка и отдельная обратная связь: путь поля, тип ошибки,
фактическая длина/лимит и предыдущий ответ только этого агента. Они передаются
следующей попытке, в том числе после продолжения. Некорректный JSON диагностируется
до проверки Pydantic; лимит защиты/последнего слова 700 проверяется до общего 1200.
Автоматического обрезания текста и молчаливого исправления игровых решений нет.

Промпты `bunker-2.1`: речь/ведущий до 1200 символов, note до 1000, ремарка до 240,
reason до 600, goal до 400. Обычные игровые ответы получают 2400 output-токенов
на весь JSON. Подготовка сохраняет отдельные бюджеты World 3000 и Character 900.
Рекомендованная длина речи 500–800, защиты/последнего слова 300–450 символов.
Потоковый клиент сохраняет до 1200 Unicode-символов; прежнего ограничения 600 нет.

После перезапуска незавершённые партии становятся приостановленными, потерянные
ответы помечаются uncertain. Выполнение у провайдера в таком случае неизвестно.
Полная запись воспроизводится без новых запросов; seed не делает LLM детерминированной.

Для DeepSeek/Alice используется строгая JSON-схема провайдера; для Qwen JSON
задаётся промптом без guided decoding, поскольку в реальной проверке оба JSON-режима
сервиса давали повреждённые ответы. Во всех случаях работают Pydantic и проверка
игровых правил. Для DeepSeek/Qwen явно отключён дополнительный reasoning. Оценка контекста через
o200k_base с запасом 30% приблизительна: фактическая токенизация моделей отличается;
ошибка переполнения API приводит к паузе, история не обрезается.

Сайт использует REST для команд и SSE для событий. Last-Event-ID восстанавливает
пропущенные события; клиент дедуплицирует отображение через снимок состояния.
Сохранение не зависит от браузера. При остановке незавершённые запросы отменяются
и отмечаются uncertain; вымышленных голосов или реплик вместо ошибок нет.

Зрительский `GET /api/games/{id}/players/{actor_id}/inspector` возвращает сохранённую
заметку, источник этой заметки и метаданные последнего игрового вызова игрока.
Подготовительные вызовы не выдаются за игровой контекст. Полный вход загружается
отдельно через существующий `/calls/{call_id}` при раскрытии в карточке.
Это архив фактических данных; при просмотре записи он явно отделён от исторической
проекции сцены. Никакие данные инспектора не добавляются в PlayerView других агентов.
